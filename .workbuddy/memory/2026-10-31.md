# 2026-10-31

## 从零搭起「弹幕蹦迪舞台」(danmaku-disco)

需求：直播弹幕驱动的可视化舞台 —— 每条评论生成一个像素小人，头顶顶着昵称在舞池蹦迪，带表情包就在头顶弹出来。目标平台：腾讯视频号 / 抖音直播 / B 站直播。

**用户当场拍板的三个选择：**
1. 弹幕接入：先做舞台 + 模拟器，真实平台接入走预留接口（不做逆向）
2. 小人风格：像素风
3. 形态：完整舞台 + 透明叠加（OBS 用）两种，可切换

**最终架构（纯前端 + 零依赖 Node 服务）：**
- `server/bridge.js`：静态托管 + HTTP POST /danmaku + WebSocket 广播，手写 WS 握手与帧编解码，无第三方依赖。端口 8787
- `js/dancer.js`：23px 高的方块小人，6 套舞步（蹦跳/举手跳/摇摆/机械舞/转圈/踏步），128 BPM，72% 的人踩同一拍点。昵称做种子 → 同一个人每次上台长得一样
- `js/stage.js`：LED 墙 + 迪斯科球 + 旋转光束 + 透视地板 + 音箱 + 后排人群剪影
- `js/overlay.js`：高清 DOM 层（名字/表情包/评论气泡/标签避让/飘屏）
- `js/danmaku.js`：统一弹幕入口，normalize() 兼容各种字段名

**关键设计决定：**
- 像素画用 640×360 低分辨率 canvas 放大（image-rendering: pixelated），中文和 emoji 用 DOM 覆盖层高清渲染 —— 既有颗粒感文字又不糊
- 标签避让：按 depth 排序，前排优先占原位，后排往上抬；抬超过 82px 开始淡出、128px 全隐藏；被抬高的牌子画引线连回头顶。牌子做透视缩放 0.82~1.12
- 三个平台差异封死在"最后一公里"之前：不管怎么拿到的弹幕，最终都是 POST `{user, text, emote, emoteUrl, platform}`

**踩过的坑（值得记住）：**
- 透明叠加模式只改 body 背景没用，**html 元素也有背景色**，得一起设 transparent（加了 JS 兜底 + CSS `:has()`）
- 一开始飘屏用 Web Animations API（`el.animate`），改成主循环 dt 驱动，顺便修掉前后追尾（上一条没完全进场就不发下一条）
- headless Chrome 的 `--dump-dom` 不驱动 rAF，DOM 快照完全不可信（会显示 0 个标签），**只有 `--screenshot` 是可靠验证手段**；反过来用它测飘屏也测不出来（元素还停在边缘被 mask 淡掉）
- 本机截图要 `--no-sandbox`，且必须用 `/Applications/Google Chrome for Testing.app`（普通 Chrome 在沙箱里起不来）

**验证结论：** 两种模式都截图确认 —— 舞台模式小人 10-18 个、标签清晰有远近层次、无明显重叠；透明模式背景干净只剩小人和名牌。服务 health / POST / 静态资源均 200。

## 追加需求：舞台和控制台拆成两个页面（同日 09:35）

用户要求"舞台和控制台分开"。拆法：

- `index.html` = **舞台页**，纯画面，删掉所有面板/按钮/连接角标。只留一个 4.5 秒后淡出的指路提示（指向 console.html，`?panel=0` 时不显示，点过一次写 localStorage 不再打扰）
- `console.html` = **控制台页**，左边 iframe 实时预览（`/?preview=1`）+ 右边所有控制项 + OBS 地址一键复制
- `js/link.js` = 两页之间的通道。同机同源走 BroadcastChannel（零延迟），同时挂 WS 走服务端中转（跨设备用）
- `js/console.js` = 控制台逻辑；`js/app.js` 里加了 `applyControl()` 接收指令

**协议**：控制台 → 舞台 `{to:'stage', type:'control', action, value}` / `{type:'danmaku'}` / `{type:'ping'}`；舞台 → 控制台 `{to:'console', type:'state', live, total, mode, source, rate, max, conn}`。

**两个坑，记住：**
1. **指令只能通过一条通道发**。Link.post 同时发 BC 和 WS 的话，舞台会从两条路各收到一次，被 execute 两遍（弹幕计数翻倍）。所以：有 BC 就只发 BC，没 BC 才走 WS；只有 `state` 这种覆盖式更新可以两条都发。
2. **配置以舞台为主人**。控制台启动时不能主动 sync 自己的配置下去 —— 否则会覆盖 OBS 用 `?mode=transparent` 打开的舞台。正确方向是控制台发 ping 问舞台要状态。

预览 iframe 也会回传 state（带 `preview:true`）。控制台分开存 real / preview 两份快照：有真实舞台就显示真实舞台的数字，没有就退而显示预览的，并在文案上写明"下面只是预览"，不让人误判。

**CSS 特异性坑**：console.html 用 `<section id="panel" class="console-panel">`，stage.css 里 `#panel{position:fixed}` 是 ID 选择器，会压过 console.css 的 `.console-panel{position:static}`。必须写成 `#panel.console-panel`。

**进程坑**：`node server/bridge.js &` 起的进程在 Bash 工具调用结束时会被回收，curl 直接 ERR_CONNECTION_REFUSED。必须用工具的 run_in_background，不要自己 `&` / nohup。


## 追加需求：舞台规格 PC 横版 / 手机竖版切换（当日 21:xx）

用户要求支持 PC 横版和竖版手机两种画面规格。做法：

- `js/dancer.js` 里加了 `SCENE_PRESETS` + `applyScene(name)`：wide = 640×360、vertical = 180×320。关键点：**两种规格的场景高度都保持 360 上下**，小人的 23px 身高在两种取景框里占比才一致；切换只是横向裁窄 + 整体轻微放大。
- `SCENE` 现在是可变对象，stage.js / app.js / overlay.js 都在运行时读它，所以切规格不用重建场景，只需重算布局
- `js/app.js` 新增 `setRatio()`：改 canvas.width/height → 按 x 比例把已在场的小人挪到新画面里 → 重新 layout → 广播新状态
- `js/stage.js` 新增 `Stage._layout()`，缓存所有布景尺寸（LED 墙行列数、桁架与光束位置、音箱宽度、地板网格、剪影人数、迪斯科球大小）按 vert 分支计算，切换时自动重排
- 所有 `vert ? a : b` 的分支都集中在 `_layout()` 里，不要散落到绘制函数的各处

**同步方案**：ratio 走和 mode 一样的 control 通道（action:'ratio'），也写进 localStorage，支持 `?ratio=vertical` 参数；控制台预览框用 `aspect-ratio` + `max-width: calc((100vh-190px)*9/16)` 跟着变形，避免竖版预览把左右栏挤爆。

**验证方法（值得复用）**：写一个临时页面把 console.html 挂进 iframe，用同域 BroadcastChannel 直接 post `{to:'stage', action:'ratio'}`，再用 `--screenshot` 截图确认预览框从 16:9 变成 9:16 —— 能在无人点击的情况下验证控制台↔舞台的控制链路。
