## 追加需求：视频号直播整包 JSON 推送接口（跨域 / 去重 / 随机消失）

用户给出一个真实抓取器的数据样例：
```
{type:'video_channel_live', capturedAt, comments:[{type:'主播',username,content,desc,capturedAt}], viewers:[{rank,name,gender,value,level,capturedAt}]}
```
要求：加个能推这种 JSON 的接口、支持跨域、推过来在舞台展示、会多次推送、保证不同名人物、特别多后随机消失。

### 服务端 `server/bridge.js`
- 新增 `POST /video-channel-live`（+ `/api/video-channel-live` 别名），`/danmaku` 带 `comments` 数组时也走同一适配
- `ingestVideoChannel()`：`comments` → `{user, text, emote, platform:'wx', isVip, source}` 逐条 broadcast；`type:'主播'` 给 VIP 名牌；`viewers` 默认不上台，`?includeViewers=1` 才上台
- **两级去重**（关键）：抓取器推的是「当前快照」，同一条会被反复推
  - 长窗口 `user+text+capturedAt`，TTL 10 分钟（seenLong Map，上限 4000，定时 sweep）
  - 短窗口 `user+text`，TTL 20 秒，兜底防脚本每次重写 capturedAt
  - 同批同名只留最后一条（倒序遍历 + batchNames Set）
- CORS：`Access-Control-Allow-Origin:*`、回显 `Access-Control-Request-Headers`、OPTIONS 204、`Access-Control-Max-Age`、支持 `Access-Control-Allow-Private-Network`（公网页面推 localhost 时 Chrome PNA 预检）
- `readBody` 统一封装，2MB 上限返回 413；`/health` 带上 seen 数量

### 舞台端 `js/danmaku.js`
- **WS 改为常连**（构造里直接 `_openWs()`），不再受「模拟器 / 外部接入」开关影响 —— 外部推送任何时候都能进舞台。开关现在只控制要不要叠加模拟弹幕
- WS `onmessage` 加过滤：跳过 `control/state/ping/sync/danmaku` 且必须有昵称或文本字段。**这条很关键** —— 同一个服务也转发控制台↔舞台的 state 心跳，不过滤会凭空长出「匿名用户」小人；`type:'danmaku'` 由 Link 通道负责，不过滤会双份
- `normalize` 兼容 `username` / `desc`
- `_emitState` 在 sim 模式且 WS open 时返回 `sim+live`，CONN_TEXT 里加了对应文案

### 舞台端 `js/app.js`
- `hub.onMessage` 改成 `enqueue`，加 `spawnQueue`（上限 200，满了丢最旧）
- **上台节拍器用 setInterval(70ms 放 2 个)，不要用 rAF 驱动** —— rAF 在后台标签页 / OBS 采集会被节流，弹幕是数据不是动画，不该跟着渲染停。这是踩过一次坑后改的：一开始把队列消费放进 frame()，headless 里 raf 只有 3~5 帧，队列根本不消费
- 开场 `hub.burst(10)` 只在 sim 模式执行（原来外部接入模式也会塞一波假人）
- `retireOldest()` → `retireRandom()`：接近上限(82%)按 40% 概率随机退人，超员退到装得下为止
- `spawn` 同名兜底：除了 byName 再用 `dancers.find` 找一次；退场清理时 `if (byName.get(d.user) === d)` 才删，避免误删同名新人的索引（竞态）
- `clearAll` 同时清 spawnQueue

## 追加需求：服务端日志 + 保底 10 人（当日 22:3x）

### 1) 服务端终端打印推送内容
- `server/bridge.js` 新增 `C`（ANSI 色）、`dispWidth()` / `fit()`（按显示宽度对齐，中文占两列）、`hhmmss()`、`logPush()`
- 每次 `/video-channel-live` 打印一个块：时间 / 来源 IP / type / capturedAt / 评论·观众条数 / 原始 JSON 字节数 → 逐条 `[主播|观众] 昵称 时间 内容 ✓上台|·同批重名|·已推过` → 观众榜前 6 → 汇总「上台 N 跳过 M」
- `ingestVideoChannel(data, includeViewers, origin, bytes)`：改为「先算每个昵称最后一次出现的位置，再按原序处理」，这样日志行能保持原始顺序并带上去向；广播顺序没变
- `broadcast()` 里对 `source === 'video_channel_live'` 跳过逐条日志，避免和上面的块重复刷屏
- JSON 解析失败 / 缺 comments 也会打印原文前 120 字（红色）
- 启动 banner 加了两行说明（会逐条打印 / 不足 10 人不退场）

### 2) 舞台不足 10 人不退场
- `js/app.js`：`MIN_LIVE = 10` + `liveFloor() = Math.min(MIN_LIVE, maxDancers)`（同屏上限比 10 还小时以上限为准，避免死锁）
- 主循环每帧先算 `holding = activeCount() <= liveFloor()`，再写进每个 `d.hold`，然后才 `d.update()`
- `js/dancer.js`：`update()` 里到点若 `hold` 则**顺延寿命** `life = age + 6 + rand*10`，而不是原地卡住 —— 这样人数上来后大家错开 6~16 秒陆续走，不会集体消失
- `spawn()` 的随机退人也加了 `live > floor` 前置条件；超员的硬循环保留

## 追加：viewers 观众榜也要出小人（当日 22:5x）

### 设计（为什么不是「直接把 viewers 当弹幕推一遍」）
观众榜是「在座名单」，每个快照都会重复带上来。若按普通弹幕处理会被 `isDuplicate` 判重（10 分钟长窗口），结果是一次上台后再也不回来 —— 人走了就永远不在台上了。所以单独走一条「续命」通道：

- 服务端 `viewerLast: Map<name, ts>` + `VIEWER_GAP = 12s`：同一位观众 12 秒内只广播一次；舞台收到同名消息本来就是 `refresh()` 续命，所以人一直站着
- 消息带 `quiet: true`（+ `role:'viewer'`）：舞台端**不弹评论气泡、不进底部飘屏、不触发欢呼**，只是站着跳舞
- 默认 `includeViewers !== '0'`（即默认开），`?includeViewers=0` 关；`?maxViewers=N` 取 rank 前 N 位，默认 20，0 = 不限
- 同批里既发言又在榜上的人只算一个，按发言处理（`batchNames` 判断）
- 前三名 `isVip` 金名牌

### 代码落点
- `server/bridge.js`：`viewerLast` + `sweepSeen` 里一起清理（60s）；viewer 循环按 rank 排序取前 N；返回体加 `viewersOnStage`；`logPush` 观众榜行给上台的人标绿色 `+`，汇总行加「其中观众榜 N」
- `js/danmaku.js`：`normalize()` 透传 `quiet` / `role`；`push()` 里 `quiet` 不累加 `total`（累计数不被观众续命刷高）
- `js/app.js`：`spawn()` 里 `if (!msg.quiet) overlay.pushTicker(msg)`；续命时不更新 `sayAt`
- `js/dancer.js`：`refresh()` 里 `if (!msg.quiet) this.hype = 1.4` —— 否则 20 个观众每 12 秒集体欢呼一次

### 验证

- 舞台端截图（注入 3 位 quiet 观众）：三个小人 + 名牌都在，没有评论气泡，底部没有飘屏
- 终端日志确认新格式：`#2 阿柯(128)+ #3 小满(66)+ #4 路人甲+` + `→ 上台 5 其中观众榜 3`
- 8787 上用户自己的进程仍是旧代码，需要重启才生效
